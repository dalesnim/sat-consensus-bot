## Phase Goal

Every question and model attempt is durably recorded, duplicate images short-circuit to a cached answer with no new spend, and the bot stays within its budget and its allowlist as real usage accrues.

This plan delivers the slice: **only people who paid can use the bot, the owner can add a buyer the moment they pay, and no single user can burn the budget alone.**

<objective>
Enforce the allowlist as the paywall and the per-user daily cap as the abuse ceiling, both before any inference spend, and give the owner `/adduser` to onboard a buyer without a redeploy.

Purpose: this is revenue protection, not politeness. Each unauthorized question is a measured $0.11 direct loss. The owner sells access out of band and admits each buyer manually — that decision is locked, so this plan builds exactly a manual allowlist and no payment integration, no access codes, and no self-service registration.

Output: a `users` table populated from env and from `/adduser`, an aiogram outer middleware that refuses unknown users before any handler runs, and an owner-only command router.
</objective>

ON CONFLICT(telegram_id) DO UPDATE SET is_allowed = excluded.is_allowed`. Upserting `is_allowed` rather than the whole row means re-seeding from env never resets a user's daily count.
  - `async def seed_allowlist(conn, ids: Iterable[int]) -> None` — `ensure_user` for each; called once at startup.
  - `async def add_user(conn, telegram_id: int) -> bool` — `ensure_user` then return whether the row was newly created, so `/adduser` can distinguish "added" from "already had access".
  - `async def is_allowed(conn, telegram_id: int) -> bool`
  - `async def try_consume_daily(conn, telegram_id: int, *, cap: int, day: str) -> bool`

`try_consume_daily` is the enforcement point and must be **one** statement, not a read followed by a write:

  `UPDATE users SET daily_count = CASE WHEN daily_count_date = ? THEN daily_count + 1 ELSE 1 END, daily_count_date = ? WHERE telegram_id = ? AND is_allowed = 1 AND (daily_count_date IS NULL OR daily_count_date <> ? OR daily_count < ?)`

Return `cursor.rowcount == 1`. A single conditional `UPDATE` is atomic in SQLite, so the allowlist check, the day rollover, the cap check and the increment all resolve together and concurrent requests cannot both pass on the last remaining slot. `.planning/research/PITFALLS.md` names check-then-act quota enforcement as the failure shape that group usage actually hits; do not split this into a `SELECT` plus an `UPDATE` for readability.

`day` is supplied by the caller as `datetime.now(UTC).strftime("%Y-%m-%d")`. UTC is the single explicit timezone for every "daily" boundary in this phase, per the same research note, and the user-facing copy says so.

Write `tests/test_access.py` covering the behaviors above, including the `asyncio.gather` concurrency case. Define fixtures locally in this module; `tests/conftest.py` is owned by plan 02-01 and must not be edited here.

Create `src/bot/middleware/__init__.py` (empty) and `src/bot/middleware/access.py` with `class AccessMiddleware(BaseMiddleware)` implementing `async def __call__(self, handler, event: Message, data: dict[str, Any]) -> Any`. Register it in `src/bot/main.py` as `dispatcher.message.outer_middleware(AccessMiddleware())`, before `include_router`, so it applies to every router in the dispatcher including the owner router added in Task 3. `deps` is available in `data` because it is Dispatcher workflow data.

Order of checks inside the middleware, each returning `None` without calling `handler` when it fails:
  1. `event.from_user is None` → log a warning and drop with no reply. An unattributable message cannot be charged to a user or capped, so it must not reach the spend path.
  2. `deps.settings.owner_id is not None and event.from_user.id == deps.settings.owner_id` → call `handler` immediately. The owner bypasses both the allowlist and the daily cap; without this, an owner who forgot to list themselves in `ALLOWED_USER_IDS` could not run `/adduser` to fix it.
  3. If the message carries neither `photo` nor `document`, check allowlist membership only with `is_allowed` and do not consume a daily slot. A `/help` or a stray text message is free; only questions count against the cap.
  4. Otherwise call `try_consume_daily(deps.db, uid, cap=deps.settings.per_user_daily_cap, day=<UTC yyyy-mm-dd>)`. On `True`, call `handler`. On `False`, read `is_allowed` once — purely to choose the refusal copy, the enforcement decision is already made — and reply with either the invite-only text or the daily-limit text.

A cache hit still consumes a daily slot. The per-user cap bounds abuse and request volume, not only cost, and treating cached questions as free would let one user flood the bot indefinitely. State this in the summary.

Refusal copy, sent through the same `Text` + `as_kwargs()` + `TelegramBadRequest` fallback pattern `ingest.py` uses:
  - not allowlisted: "This bot is invite-only. If you've paid for access, message the owner with your Telegram ID and they'll add you."
  - cap reached: "You've used all {cap} of today's questions. The limit resets at midnight UTC."
Neither message reveals whether a given id exists in the database.

If a database error occurs anywhere in the middleware, log at `error` and refuse. This is the one place in the phase that fails **closed**: the allowlist is the paywall, and an unavailable database must not become open access.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram user → middleware | `from_user.id` is supplied by Telegram, not by the user's message body, and is the only identity the bot has |
| Command argument → SQL | `/adduser <arg>` is fully attacker-controlled text |
| Allowlist state → spend | Whatever the middleware admits becomes billable OpenRouter traffic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-13 | Elevation of privilege | `/adduser` | mitigate | Owner check performed twice — once in `AccessMiddleware`, once inside the handler — and refused entirely when `OWNER_ID` is `None`. `from_user.id` comes from the Telegram update envelope and cannot be set by message content. |
| T-02-14 | Spoofing | allowlist bypass | mitigate | The middleware is an **outer** middleware on `dispatcher.message`, so it runs before every router in the dispatcher; no handler can be reached without passing it. A database error inside it refuses rather than passes. |
| T-02-15 | Tampering | SQL injection via `/adduser` | mitigate | The argument is cast with `int()` before use and bound as `?`. Grep criterion forbids f-string SQL in `handlers/owner.py` and `db/users.py`. |
| T-02-16 | Denial of service | one user draining the budget | mitigate | Atomic single-statement `try_consume_daily` caps each user at `PER_USER_DAILY_CAP` per UTC day; concurrency cannot race past it. |
| T-02-17 | Denial of service | unattributable updates | mitigate | `from_user is None` is dropped before the spend path. |
| T-02-18 | Information disclosure | allowlist enumeration | mitigate | The refusal copy is identical whether an id is absent or explicitly disallowed, so a probe cannot distinguish the two. |
| T-02-19 | Repudiation | who was granted access and when | mitigate | `users.added_at` records the UTC grant time for every row, including env-seeded ones. |
| T-02-SC | Tampering | package installs | n/a | This plan installs no new packages. |
</threat_model>
