## Phase Goal

Every question and model attempt is durably recorded, duplicate images short-circuit to a cached answer with no new spend, and the bot stays within its budget and its allowlist as real usage accrues.

This plan delivers the last slice and closes the phase: **the owner can read the unit economics of their own product from inside Telegram, and the whole phase is verified against the live bot.**

<objective>
Give `OWNER_ID` a `/cost` command reporting spend today, spend this week, cost per question, and cache hit rate — then verify every behavior of the phase end to end against the running bot.

Purpose: the owner cannot price a product whose per-question cost they do not track. `/cost` is a business tool, not a debug command. It is also the only place the cap, the reservation ledger, the cache, and the question volume are visible together, which makes it the first place a broken cost path shows up.

Output: a cost aggregate module, the `/cost` handler on the existing owner router, README operator notes, and a blocking human verification of the whole phase.
</objective>

    - `build_cost_report` on an empty database returns zeros for every figure and does not raise
    - `spend_today` equals the `actual_usd` of the current UTC day's `spend_days` row
    - `spend_week` sums `actual_usd` across the seven UTC days ending today inclusive
    - `questions_today` counts `questions` rows whose `created_at` day equals today, including cache-served rows
    - `cache_hits_today` counts only rows with `served_from_cache = 1`
    - `cost_per_question_today` divides today's actual spend by the count of today's non-cache-served questions, and returns `0.0` when that count is zero
    - `cache_hit_rate_today` returns `0.0` when there were no questions today
    - `reduced_rounds_today` counts rows with `reduced_model_set = 1`
    - A question created on the previous UTC day is excluded from every "today" figure
  </behavior>

  <action>
Create `src/bot/cost/report.py` with a frozen `CostReport` dataclass carrying `day: str`, `spend_today: float`, `reserved_today: float`, `cap_usd: float`, `spend_week: float`, `questions_today: int`, `cache_hits_today: int`, `reduced_rounds_today: int`, `cost_per_question_today: float`, `cost_per_question_all_time: float`, `cache_hit_rate_today: float`; and `async def build_cost_report(conn, *, cap_usd: float, now: datetime) -> CostReport`.

`now` is injected rather than read inside the function so the day-boundary behaviors are testable without freezing the clock. Callers pass `datetime.now(UTC)`.

Derive the UTC day key as `now.strftime("%Y-%m-%d")` and the week as the seven day keys ending today inclusive. Query `spend_days` with `WHERE day BETWEEN ? AND ?` for the week sum. Query `questions` with `WHERE substr(created_at, 1, 10) = ?` for today's counts, which works because `created_at` is written as a UTC ISO-8601 string with a `YYYY-MM-DD` prefix. All parameters bound with `?`.

`cost_per_question_all_time` is `SUM(cost_usd)` over `attempts` divided by the count of `questions` rows with `served_from_cache = 0`, guarded against a zero denominator. Using `attempts` rather than `spend_days` for the all-time figure means the number survives even if the ledger is ever reset, and the two should agree — a divergence between them is itself a useful signal.

UTC is the timezone for every daily boundary in this phase, matching `try_consume_daily` and the spend ledger. `.planning/research/PITFALLS.md` specifically flags a mismatch between the server's day boundary and the owner's expectation as a way caps surprise people; the fix is picking one explicit timezone and saying so in the `/cost` output, which Task 2 does.

Write `tests/test_cost_report.py` covering the behaviors above, seeding rows with explicit `created_at` values on both sides of a UTC midnight. Define fixtures locally.
