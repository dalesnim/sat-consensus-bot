## Phase Goal

Every question and model attempt is durably recorded, duplicate images short-circuit to a cached answer with no new spend, and the bot stays within its budget and its allowlist as real usage accrues.

This plan delivers the slice: **the owner's OpenRouter balance cannot be drained — by a bug, an abuser, or a burst of simultaneous questions — and when the day's budget runs out the bot keeps working on a cheaper roster and tells the user it did.**

<objective>
Enforce the global daily spend cap with an atomic conditional reservation taken before any model is called, and fall back to a reduced cheaper model set above the cap.

Purpose: unit cost is margin now. Live measurement puts a full round at $0.11, of which Opus alone is $0.058 and GPT-6 Astra a further $0.024. Dropping those two leaves `{sonnet, gpt-5.6-sol, gemini, mistral}` at roughly $0.029 — a 74% saving that still spans four labs, so the lab-diversity property the ensemble depends on survives the downgrade. ACC-04 requires atomic enforcement specifically because the obvious implementation is a textbook TOCTOU race that a study group sending questions in the same few seconds will actually hit.

Output: a `spend_days` ledger with a conditional-update reservation, a guard that picks full / reduced / refuse, a `run_round` that accepts a model subset, and a reply line that discloses the downgrade.
</objective>

  <action>
Create `src/bot/db/spend.py` with `?`-bound statements only.

`async def reserve(conn, *, day: str, amount: float, cap: float) -> bool` performs exactly two statements:
  1. `INSERT OR IGNORE INTO spend_days (day) VALUES (?)` — idempotent seeding; two coroutines both attempting it is harmless.
  2. `UPDATE spend_days SET reserved_usd = reserved_usd + ? WHERE day = ? AND reserved_usd + ? <= ?`

Return `cursor.rowcount == 1` from the second statement. This is the whole enforcement mechanism. The condition and the increment live in one SQL statement, so SQLite resolves them together and there is no window between the check and the write for another coroutine to slip through. `.planning/research/PITFALLS.md` names this exact requirement: "a single atomic conditional update, not a read-then-write," and calls the read-then-write variant never acceptable for this project because it is explicitly load-bearing. Do not add a `SELECT` before the `UPDATE`. Do not add an `asyncio.Lock` in place of the SQL condition.

Seeding with a bare `INSERT OR IGNORE` and letting the conditional `UPDATE` do all the work also closes the first-request-of-the-day hole: a fresh row starts at `reserved_usd = 0`, so an amount larger than the cap fails the `WHERE` and is refused rather than silently admitted.

`async def reconcile(conn, *, day: str, estimate: float, actual: float) -> None` runs one statement: `UPDATE spend_days SET reserved_usd = MAX(0, reserved_usd - ? + ?), actual_usd = actual_usd + ? WHERE day = ?` bound with `(estimate, actual, actual, day)`. `reserved_usd` therefore always means "already spent today plus currently in flight", which is the correct quantity to compare against the cap. The `MAX(0, ...)` guards against a reservation being released twice by a retry.

`async def day_totals(conn, day: str) -> tuple[float, float]` returns `(reserved_usd, actual_usd)`, or `(0.0, 0.0)` when no row exists.

Write `tests/test_spend.py` covering every behavior above, with the twenty-way `asyncio.gather` concurrency case asserting exactly seven admissions. That test is the proof ACC-04 asks for; it is not optional and it must run against a real SQLite file, not a mock.
  </action>
