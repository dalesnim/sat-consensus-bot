## Phase Goal

Every question and model attempt is durably recorded, duplicate images short-circuit to a cached answer with no new spend, and the bot stays within its budget and its allowlist as real usage accrues.

This plan delivers the first user-observable slice of that goal: **the owner can open the database after any question and see exactly what happened** — which models answered, what each of them read off the image, what each of them cost, and which of them failed.

<objective>
Stand up SQLite persistence and write every round to it: one `questions` row plus one `attempts` row per model, on the real live path, after every question a user asks.

Purpose: DATA-03, DATA-04 and DATA-06 are the audit substrate. Nothing else in this phase — the cache, the spend cap, `/cost` — can exist without rows to read. DATA-06 in particular is a silent-failure detector: correlated OCR hallucination (all six models reading the same degraded image and fabricating the same passage) is invisible in the reply and only detectable by querying the stored transcriptions and their overlap score afterwards.

Output: `src/bot/db/` package (connection, schema, two repositories), a `db` field on `Deps`, and a persistence call at the end of `answer_question`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram user → handler | `message.from_user.id`, `file_id`, and image bytes are attacker-controlled |
| Model response → database | `Verdict` fields including `passage_transcription` are model-generated free text written into `raw_json` |
| Process → SQLite file | The only durable store; holds user ids and copyrighted passage text |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | `db/questions.py`, `db/attempts.py` | mitigate | Every statement uses `?` parameter binding; no f-string or `%` SQL construction. Enforced by the grep acceptance criterion in Task 2. |
| T-02-02 | Information disclosure | `attempts.raw_json` | mitigate | Store only the validated `Verdict` plus the malformed pre-repair text truncated to 4000 chars. Never store the base64 image, the `Authorization` header, or the raw HTTP response envelope. The existing `DEBUG_LOG_RAW_BODIES=false` default already keeps request bodies out of logs. |
| T-02-03 | Information disclosure | `questions.user_id` | accept | A Telegram numeric id is a pseudonymous identifier and is required to enforce the allowlist and per-user cap (ACC-01, ACC-03). No name, username, or message text is stored. |
| T-02-04 | Information disclosure | `questions` / `attempts` passage text | accept | Model transcriptions of College Board practice questions are stored deliberately — DATA-06 cannot detect correlated OCR hallucination without them. This is a recorded IP-exposure consideration in PROJECT.md, not a code defect. |
| T-02-05 | Denial of service | shared aiosqlite connection | mitigate | WAL mode plus `busy_timeout=5000` set once at connection open, per the `database is locked` finding in `.planning/research/PITFALLS.md`. |
| T-02-06 | Denial of service | persistence failure on the reply path | mitigate | The persistence block is wrapped in `try/except` and logged; the user still receives the already-paid-for reply. |
| T-02-07 | Repudiation | round auditability | mitigate | `created_at` in UTC ISO-8601, plus per-attempt cost, tokens, latency and error, make every spend event reconstructable. |
| T-02-SC | Tampering | `pip install aiosqlite` | mitigate | `aiosqlite==0.22.1` is a locked-stack package in PROJECT.md, verified live against the PyPI JSON API in `.planning/research/STACK.md` on 2026-09-10. Status `[VERIFIED]`; the pinned version must not be floated. |
